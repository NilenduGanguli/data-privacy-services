  • 642,318 rows in LOANS.APPLICANTS are updated by APPLICATION_ID: 13 columns each, in batches of 5,000 per partition across 8 partitions.
  • Loan origination screens and credit reports that read LOANS.APPLICANTS see protected values as each batch commits.
  • The originals can be restored only with the key returned when the job finishes. The key is shown once and DPS keeps no copy; if it is lost, the original values cannot be recovered.
  • Synthetic values have no path back. After the write, the original values in these 13 columns are gone.
  • PIN_CODE and CIBIL_SCORE use one-way methods (generalize, bucket). Those two columns cannot be restored, even with the key.
  • If a partition fails it resumes from its last committed batch. No row is left half-written.
  • LOANS.APPLICANTS grows from 1,873,512 to 2,515,830 rows. Existing rows are not changed.
  • New rows get APPLICATION_ID = original + 90,000,000, up to 108,406,552. The evidence pack records the range.
  • Reports and jobs that read LOANS.APPLICANTS will count the new rows until you remove them.
  • The key that reverses the new rows is returned once when the job finishes. DPS keeps no copy.
  • The new rows are synthetic and have no path back to real applicants.
