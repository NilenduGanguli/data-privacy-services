## 0. Ground rules carried from M0 (all milestones)

1. **No values anywhere they could persist or leak.** Never log, print, put in an exception message, a
   metric label, an audit row, a job row, an evidence pack or an artefact name: a customer value, a
   key/DEK/seed, a token-to-original mapping, a password, a connection string with credentials, a
   storage-state file. Allowed: counts, entity types, method names, JSON paths / column names, value
   *shapes* (§5.4), `hash_value()` correlation ids, kids, error *codes*. The structlog allow-list in
   `dps/observability.py` (`_drop_value_fields`) is extended — never bypassed — by each milestone, and each
   milestone adds a log-scan test for its new modules (`tests/test_no_values_in_logs_<milestone>.py`).
2. **Fail closed.** Verification failure under `verify.leakage_check: strict` writes nothing for that unit
   (request, batch, page) and fails it with code `leakage`.
3. **The engine is the only transformer.** L1/L2/L3 never implement a masking method; they build
   `Plan`s and call `dps.engine.transform.apply.apply_plan` (or the façade). `dps/engine/transform/crypto.py`
   stays the only module that touches key bytes, plus `dps/secrets.py` (§6.3) for at-rest sealing.
4. **Gates per task** (unchanged from M0, extended): `ruff check dps tests tools && ruff format --check dps
   tests tools && mypy dps && pytest -q`; when `frontend/` changes, `cd frontend && npm run typecheck &&
   npm run build`. Integration gates per milestone are in §12.4.
5. **Git.** Author = global identity (NilenduGanguli). **No `Co-Authored-By` or any other trailer.**
   Conventional commits. Stage and commit with an explicit pathspec (`git add <paths> && git commit -m
   "…" -- <paths>`); never `git add -A/.`, `commit -a`, `stash`, `reset`, `checkout --`, `clean`. Never run
   git against the parent `~/document_intelligence` repo.
6. **HANDOFF.md** is updated in the same commit as any build/run/deploy/config change (the Wega rule).
7. **Interfaces are defined once.** If a later milestone needs to change an M0 module (e.g. `apply.py`),
   it changes that module *and its tests* together and lists it in its plan's "M0 touch points".

**Amendment 2026-10-12 (lane-safe compose).** Milestones are built in parallel lanes, each with its own
stack on the same host, so nothing in the local stack may be fixed to one lane:

- **Host ports.** Every host port mapping in `docker-compose.yml` uses a variable whose default is the
  contract port: `127.0.0.1:${DPS_APP_PORT:-8400}:8400`, and likewise `DPS_DB_PORT` 5441,
  `DPS_SOURCE_PG_PORT` 5442, `DPS_MINIO_PORT` 9010, `DPS_MINIO_CONSOLE_PORT` 9011, `DPS_ORACLE_PORT` 1522,
  `DPS_MONGO_PORT` 27018, `DPS_OCR_PORT` 5016, `DPS_DEMO_SITE_PORT` 8410, M5's `DPS_TOKENIZER_MOCK_PORT`
  8420, and any worker metrics port a milestone publishes on the host (`DPS_WORKER_METRICS_PORT` 9400,
  `DPS_BROWSER_WORKER_METRICS_PORT` 9401). Container ports and in-network names (§11) never change.
- **Images.** Every image compose builds is tagged from `DPS_IMAGE_TAG`:
  `data-privacy-services:${DPS_IMAGE_TAG:-local}` (app, `migrate`, `worker` and every other service that
  runs the app image), `data-privacy-services-browser:${DPS_IMAGE_TAG:-local}` (M4) and
  `document_intelligence-azure-ocr-mock:${DPS_IMAGE_TAG:-latest}` (M1). Pulled images (`postgres`,
  `minio`, `mongo`, `oracle-free`, `node`) keep their pinned tags.
- **Plan snippets.** A literal host port or image tag anywhere in any plan — compose snippets, test code
  and fixtures, tools, `.env` examples, manual checks and gate commands — is superseded by this rule:
  implement it in the variable form. Shell and compose write `${DPS_*_PORT:-<contract port>}` and
  `${DPS_IMAGE_TAG:-…}`; code reads the `DPS_TEST_*` variable first and otherwise builds the default
  from the `DPS_*_PORT` variable (§12.2), as `tools/smoke_test.py` does with `DPS_APP_PORT`. A test
  may assert a contract port only with that port variable unset.
- **Tests and tools** read endpoints only from the `DPS_TEST_*` variables of §12.2 (whose defaults follow
  the port variables above), never from a literal host port, so a lane moves its ports by exporting the
  same variables to compose and to pytest/tools.
- A lane also sets `COMPOSE_PROJECT_NAME` (e.g. `dps-m2`) so containers, networks and volumes do not
  collide with another lane's stack. HANDOFF.md §3 documents the convention. A container a plan starts
  outside compose (`docker run --name …`) carries `${COMPOSE_PROJECT_NAME:-dps}` in its name for the
  same reason.

**Amendment 2026-10-12 (surrogates never reuse a part of the record; A-prepare review r1, B1).** Under
`en_IN` Faker drew the customer's own surname, or a surname or street holding it, in about one record in a
hundred, and the whole-value sweep passed. M0 now changes three interfaces, additively:

- `apply_plan` and `synthesize_text` hand the record's detected values to the surrogate engine before any
  field (`dps.engine.transform.methods.declare_record(provider, anchor, [(entity_type, original), …])`,
  protocol `RecordAwareSurrogates`; a provider without it, such as a test double, is left alone). The
  record's persona then shares no part with its names (name, e-mail, username, street, city, MRZ
  holder), and a surrogate that would hold another of the record's values (normalised, ≥ 4 characters) or
  a part of its names is drawn again. Code that calls `SurrogateEngine.surrogate` for a record outside
  those two functions calls `declare_record` first.
- `PersonaFactory.for_anchor(…, avoid=…)` and `SurrogateEngine.persona(anchor, locale, avoid=…)` take the
  name parts to avoid; a persona that does not collide is unchanged.
- `verify_output(…, source=…)` (the input document or text) also checks each part (≥ `min_len`) of a
  detected, transformed name, counted per output string against the input outside the names. The L1
  service passes it. §6.4's per-row sweep decides whether to pass it, by the same volume reasoning as
  its cross-field rule.

**Amendment 2026-10-12 (`fpe_digits` keeps the leading-zero class; M2 review G4 r1, B1).** Plain FF1 turns
about one value in ten into a token that starts with `0`. An integer or decimal column stores that token
without its first digit, and reveal then returns a different number without an error (probe: 34 of 300
`bigint` ids wrong, 23 of 300 `numeric(14,2)` amounts unrevealable), which also breaks every `date_shift`
reveal of those rows (the anchor is recomputed from the revealed key, §6.2). Decided at contract level,
for every layer, so that the same digits keep one token everywhere (P3, §6.5):

- `fpe_digits` takes `leading_zero: any | preserve`. `preserve` cycle-walks FF1 when `keep_prefix` is 0:
  FF1 is applied again to its own output until the token's first digit is `0` exactly when the value's
  is. It is a bijection on each class (reversed by walking back with decryption), keeps the length, and
  leaves unchanged every token that plain FF1 already started with a non-zero digit (about 90 % of
  values without a leading zero). With a kept prefix the first digit is kept anyway, so nothing changes.
  The method's own default is `any`, so a reveal hint or a reveal map without the param means plain FF1
  and the tokens issued by v0.1.0-m0 still reveal.
- Every **new plan** gets `preserve`: `PlanEntry` (`dps.engine.findings.PLAN_PARAM_DEFAULTS`,
  `with_plan_defaults`) and §6.4's `ColumnPlan` complete an `fpe_digits` spec that leaves `leading_zero`
  out, so L1 plans, L1 reveal hints, L2/L3 column plans and the evidence pack's `reveal_map` all carry it
  explicitly. The policy object and its `config_hash` are unchanged. A policy may still say
  `leading_zero: any` (for example to match tokens issued before), except on a numeric column (below).
- `dps/engine/transform/fpe.py`: `fpe_digits_encrypt/decrypt(…, preserve_leading_zero: bool = False)`,
  `cycle_walk_leading_zero(step, digits)`, `CycleWalkError(ValueError)` and `MAX_WALK = 1000` (a real
  permutation exceeds it with probability below 1e-45; a cipher that is not a permutation fails with a
  value-free `MethodError` instead of looping).
- `BatchTransformer` refuses `fpe_digits` without `leading_zero: preserve` on an `int`/`decimal`/`float`
  output column (`IncompatibleMethod`, `incompatible_method`) and a `ColumnPlan` whose method params
  lack their plan defaults (`ValueError`: a plan copied around its validator would run with params its
  reveal map does not show). Any reversible output that the target column's codec would store
  differently (`to_engine_text(from_engine_text(text)) != text`: a dropped leading zero, a decimal
  re-scaled to the column's scale, a `float` that does not round-trip) fails the batch with
  `incompatible_method` instead of being written.

**Amendment 2026-10-12 (the write guard is the caller's mark; same-table append keys; M2 review G5 r1,
B1–B3).** A worker process keeps one writer per job, which every holder of a partition in that process
shares — a zombie whose lease was reclaimed and the re-claimed holder alike — and a partition's first batch
had no ledger row to lock, so the "never apply a batch twice" rule of §4.2 did not hold under lease loss.
Probes applied an in-place batch twice and appended a first batch twice. Binding for every writer (§4.2,
M3's Oracle and Mongo writers included):

- `write_batch` applies a ledgered batch only when the partition's ledger holds `mark.batch_no - 1`, read
  under a lock in the batch's own transaction; anything else is `LedgerConflict` (`ledger_conflict`, nothing
  written; the holder stops quietly). The expected batch comes from the caller's mark (its own resume point:
  the ledger mark, else the partition checkpoint), never from writer-instance state.
- The partition's ledger row is created (`batch_no = 0`) before it is locked, in the same transaction
  (PostgreSQL `INSERT … ON CONFLICT DO NOTHING`), so a concurrent first batch waits for the other holder's
  open transaction instead of finding no row to lock. `read_ledger` treats a `batch_no = 0` row as no mark.
  A ledgered batch whose rows are empty still records its mark, so batch numbers stay contiguous.
- `files`: a spool takes each batch number exactly once and in order (`mark.batch_no` must follow the
  spool's last batch, else `LedgerConflict`), every spool has its own local folder, and
  `finish_partition(…, batch_no=<the caller's last batch>)` uploads only a spool that ends with that
  batch (else `LedgerConflict`, nothing uploaded). `batch_no` is a new optional keyword of
  `BatchWriter.finish_partition`; database writers ignore it.
- A partition whose ledger is behind its checkpoint (only possible when ledger rows were removed) is
  failed with `ledger_conflict` instead of being written again: which batches were applied is unknown.
- Same-table `append` (§5.3): `offset` must lift every selected key above the table's largest key
  (`min(selected key) + offset >= max(key) + 1`, checked at prepare; a shifted key that lands in a key gap
  below that bound would sit inside a partition range and be read and appended again), and `generate` needs
  an owned (`pg_get_serial_sequence`), ascending, non-cycling sequence ahead of the table. Both are
  `pk_strategy_invalid`.

- GUC: **`app.tenant_id`**, set with `set_config('app.tenant_id', $1, false)` on checkout, reset to `''` on
  release. Every tenant-scoped query runs inside `acquire(tenant_id)`.
- Runner: files `dps/migrations/NNN_<slug>.sql` sorted by name; `__SCHEMA__` replaced by the validated
  `settings.pg_schema` (`^[a-z_][a-z0-9_]{0,62}$`); each file runs in one transaction under
  `pg_advisory_lock(hashtext('dps.migrate.' || schema))`; ledger `__SCHEMA__.dps_migration_ledger(filename
  text PK, checksum text NOT NULL, applied_at timestamptz NOT NULL DEFAULT now())`; an applied file whose
  checksum changed refuses boot (`MigrationDrift`). **Applied files are never edited** — fix forward.
- `DPS_MIGRATIONS_MODE`: `auto` (local/dev: app and worker run pending migrations at boot as the
  migration role), `verify` (staging/prod: boot fails on pending or drifted files), `off` (tests that
  manage the schema). Posture requires `verify` in staging/prod.
- `python -m dps.migrate` applies; `--verify` only checks; `--maintain` creates audit partitions

- Readiness: the app sets component `db` (`ok`, detail `up|down|unconfigured`) and `jobs` (`ok` when `db`
  ok and migrations verified). `api-core` never depends on them (spec §4 "statelessness, precisely").

## 3. Job model and workers (M2; scan kind used by M4)

### 3.1 Kinds, phases, states

| Kind | Id prefix | Phases (in order) | Claimed by | Created by |
|---|---|---|---|---|
| `discover` | `j_` | `discover` | `worker` | `POST /api/v1/jobs/discover` |
| `run` | `j_` | `prepare` → `partitions` → `finalize` | `worker` (job rows + partitions) | `POST /api/v1/jobs/run` |
| `scan` | `s_` | `scan` | `browser-worker` only | `POST /api/v1/scans` |
| `retention` | `j_` | `retention` | `worker` | the worker scheduler, every `DPS_RETENTION_INTERVAL_HOURS` |

Job `state`: `queued` (claimable when `run_after <= now()`) · `running` (leased) · `waiting` (run job in
`partitions` phase; not claimable itself, its partitions are) · `paused` (no new partition claims; running
partitions stop after their current batch and go back to `queued`) · terminal `succeeded | failed | dead |
canceled`. Partition `state`: `queued | running | done | failed | dead | canceled`.

Transitions (all fenced on `locked_by` + `state='running'` for worker writes):

- run `prepare` success → insert partitions, set `phase='partitions', state='waiting'`, release lease.
  `dry_run` → `phase='finalize', state='queued'` (no partitions, no writes, no DDL).
- partition `done` → in the same transaction: if no partition of the job is non-terminal, set the job
  `phase='finalize', state='queued', run_after=now()` (`UPDATE … WHERE phase='partitions' AND NOT EXISTS
  (…)`). Any partition `dead` → job still finalizes, with outcome `failed`.
- `finalize` → evidence pack, artefacts, purge `key_enc`, terminal state, `expires_at = now() + retention`.
- cancel: queued/waiting/paused → `canceled` immediately (partitions `canceled`); running → `canceled` and
  holders notice on the next fenced write (zero rows) and stop. Finalize still runs a *cancel* finalize
  (evidence with `outcome: canceled`, key purge) — scheduled as `phase='finalize', state='queued'` with
  `progress.outcome='canceled'`.
- retry (API): only `failed|dead` run jobs; requeues failed/dead partitions (attempts reset) and resumes
  from their checkpoints; refused when `key_enc` was purged and the caller did not resubmit key material
  (`409 key_material_required`, body may carry `consistency.key_material`).

### 3.2 Queue mechanics (`dps/jobs.py`)

Mirrors `di/jobs.py`: FIFO by `(priority, run_after, created_at, id)`, two-level claim (cap-aware
candidate CTE → inner `FOR UPDATE SKIP LOCKED` with state re-check), lease + heartbeat at `lease/4`,
reaper with exponential backoff + jitter, dead-letter at `max_attempts`, `pg_notify('dps_job_new', kind)`
on enqueue and on partition/finalize becoming claimable, LISTEN on a dedicated non-pooled connection with
poll fallback. Caps: per tenant, running partitions + running job rows ≤ `dps_tenant.max_running` (default
`DPS_JOB_TENANT_MAX_RUNNING`); per run job, running partitions ≤ `spec.source.parallelism`; queued jobs per
tenant ≤ `max_queued` (accept-side 429 `queue_full`).

Amendment 2026-10-12 (M2 review G2 r1): `create_job` serialises admission per tenant
(`pg_advisory_xact_lock(hashtextextended('dps_job_admit:<schema>:<tenant>', 0))` before the count), so
concurrent submissions cannot pass `max_queued` together, and a replay that waited behind the lock returns
the original job. Every `reap` pass finalizes each `partitions`-phase job (`waiting`/`paused`) that has no
`queued`/`running` partition left, so a pass interrupted after its dead-letter commit cannot strand a job
(or its `key_enc`). `PartitionView.checkpoint_fp` is keyed: the first 8 hex of
`HMAC-SHA256(HKDF-SHA256(job KEK, salt=job id, info="dps.checkpoint_fp"), canonical encoded last_key)`
(`dps.secrets.keyed_fingerprint`, `base.key_fingerprint(encoded, *, kek, job_id)`), so a reader of the job
cannot recover a key by enumerating the key space; `None` when no KEK is configured.

### 3.4 Leases and timings (defaults)

Job rows `DPS_JOB_LEASE_SECONDS=300`; partitions `DPS_PARTITION_LEASE_SECONDS=120`; heartbeat every
`lease/4`; job `max_attempts=3`, partition `max_attempts=5`; reaper every 30 s; backoff `30 s · 2^attempts`
capped at 3600 s with ×(0.5–1.5) jitter. A worker that loses a fenced write cancels the local task at once.

### 3.6 Retention job

One module, one scheduler, one system tenant:

- **Handler:** `dps/retention.py::retention_job(ctx, job)` (M2). M5 extends the same module (new tables,
  `run_retention`, `RetentionCounts`, roll-up refresh) and never creates a second one.
- **Scheduler:** `jobs.ensure_retention_job(settings.retention_interval_hours)`, called from the `Consumer`
  reaper loop of every worker whose `kinds` include `retention`. It inserts the job with
  `idempotency_key = f"retention:{bucket}"` (`bucket = floor(epoch / interval)`), so the unique index
  `dps_job_idem` makes it at most one per interval across all replicas. No other scheduler exists. On-demand
  runs (M5 `POST /admin/retention/run`) call `create_job(tenant_id=SYSTEM_TENANT, kind=retention, ...)`
  without an idempotency key.
- **System tenant:** retention jobs belong to `jobs.SYSTEM_TENANT = "_system"` (it has a `dps_tenant` row,
  allowed by the 002 CHECK). Its own expired retention jobs are deleted by the same per-tenant loop as any
  other tenant's (terminal jobs get `expires_at` like every job). `_system` is never accepted from an API
  caller (§8.1).

Deletes (as `dps_worker_login`, per tenant, GUC bound; tenants = `dps_tenant` ∪ distinct `dps_job.tenant_id`,
M5: `tenant_directory(include_system=True)`) jobs with `expires_at < now()` (cascade to partitions, evidence, artefact rows and
M4's scan rows — `dps_scan_page/field/request/event` all reference `dps_job ON DELETE CASCADE`; snapshots keep
living with `job_id` set null) after deleting their objects from the `ObjectStore`; deletes
`proposed`/`superseded` snapshots older than the retention window (accepted snapshots live until
superseded); nulls `dps_connection.secret_enc` where `secret_expires_at < now()`; nulls `key_enc` on any
terminal job (defence in depth). Never touches `dps_audit_log` (that is `migrate --maintain`) and never
exported files (customer output).

Rules every implementation obeys (enforced by `tests/connectors/conformance.py`, run against all three):

- **Source reads are read-only** (`BEGIN READ ONLY` + `statement_timeout` on PG; no `FOR UPDATE` anywhere;
  Oracle reads never lock; Mongo reads with `readConcern: majority` when a replica set is present).
- Keyset predicate: `key >= lower AND key < upper AND key > after_key`, ordered by key. Composite keys:
  PG row-value comparison; Oracle expanded form `a > :a OR (a = :a AND b > :b)`; Mongo `_id` only.
- `FETCH FIRST n ROWS ONLY` / `LIMIT` only in statements without `FOR UPDATE` (Wega L21).
- Identifiers are only ever interpolated after `selection.quote_ident(name, engine)` (§5.2).
- **Write atomicity / resume.** For `in_place` and `append` the writer keeps a ledger in the target
  database — table `DPS_WRITE_LEDGER` (PG/Oracle; schema = `target.ledger_owner` or the target owner)
  or collection `dps_write_ledger` (Mongo) — with `(job_id, partition_no) → (batch_no, last_key)` updated
  **in the same transaction** as the batch. On resume, the worker takes the ledger mark as authoritative
  over `dps_job_partition.last_key` (they can differ by one batch after a crash), so a batch is never
  applied twice (an in-place re-obfuscation would corrupt data). The guard is the caller's mark: a batch
  is applied only when the locked ledger row holds `mark.batch_no - 1`, and the row is created with batch 0
  before it is locked, so a first batch is serialised too (§0 amendment 2026-10-12, G5 r1). `table` loads are idempotent upserts on
  the key and need no ledger; `files` writes one object per partition, uploaded on `finish_partition`
  (a resumed partition rewrites its object from the start). The ledger rows of a job are deleted at
  finalize; the ledger table is created by `prepare` (Oracle 19c-safe: PL/SQL that ignores ORA-00955).
- `in_place`: `UPDATE … SET <transformed cols> WHERE <key> = …` in `executemany` batches; key columns are
  never in the SET list. The table is assumed quiescent (documented; DPS does not lock).
- `table` + `truncate_insert`: `prepare` truncates once (guarded by job phase); rows then upsert on key
  (PG `INSERT … ON CONFLICT (key) DO UPDATE`, PG bulk via `COPY` into a temp table + `INSERT … SELECT …
  ON CONFLICT`; Oracle `MERGE`; Mongo `bulk_write(ReplaceOne(upsert=True), ordered=False)`).
- Mongo `in_place`/`append(generate)` need transactions → replica set (`capabilities.transactions`); a
  standalone server is refused at `prepare` with `transactions_unsupported`.
- Engine notes from the spec carried as tests (M3): Oracle pool `expire_time=1`, `call_timeout`
  (`DPS_ORACLE_CALL_TIMEOUT_MS`), `tcp_connect_timeout=10`, `module="dps"`, `action=<job phase>`,
  `client_identifier=<job id>`; `cursor.arraysize = cursor.prefetchrows = batch`; CLOB/NCLOB fetched as
  `str` (`oracledb.defaults.fetch_lobs = False`) and never addressed with `DBMS_LOB` offsets (UTF-16
  units); CHAR key binds via `setinputsizes(oracledb.DB_TYPE_CHAR)`; key columns with `ts_precision > 6`
  are selected as `TO_CHAR(c, 'YYYY-MM-DD"T"HH24:MI:SS.FF9')` and bound back with `TO_TIMESTAMP(:k, …)`.
  Required tests: `test_oracle_clob_astral_roundtrip`, `test_oracle_char_key_paging`,
  `test_oracle_timestamp9_key_paging`.

Identifier rules: Oracle `^[A-Za-z][A-Za-z0-9_$#]{0,127}$` (upper-cased, double-quoted — the Wega rule);
PG `^[A-Za-z_][A-Za-z0-9_$]{0,62}$` (double-quoted as given); Mongo field paths
`^[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)*$`. SQL text: `sqlglot.parse(…, read="postgres"|"oracle")`
must yield exactly one `Select` (where is parsed as `SELECT 1 FROM t WHERE <expr>`); rejected: any DML/DDL
node, `INTO`, `FOR UPDATE`, `;`, and functions on the deny-list (`pg_sleep`, `pg_read_file`, `lo_*`, `dblink*`,
`dbms_*`, `utl_*`, `sys.*`, `xmltype`, `httpuritype`; M2 adds `set_config`, `pg_terminate_backend`,
`pg_cancel_backend`, `pg_advisory*`, `pg_reload_conf`, `pg_rotate_logfile`, `pg_promote`, `pg_ls_dir`,
`pg_stat_file`, `lo_import`, `lo_export`; positional `$n` binds are refused — named `:name` only). `query` must project every key column, is wrapped as
`SELECT * FROM (<query>) q WHERE <keyset>`, and is refused for `in_place`. Mongo filter operators
allow-list: `$eq $ne $gt $gte $lt $lte $in $nin $and $or $nor $not $exists $type $size $all $elemMatch
$regex`; anything else (`$where`, `$expr`, `$function`, `$accumulator`, …) → `selection_operator_denied`.

## 6. L2/L3 → engine bridge (`dps/engine/batch.py`)

### 6.1 Key material per job / job group

- **obfuscate**: one `KeyMaterial` per run job; if `consistency.key_material` is given it is used
  (`key_material_from_caller`), else `generate_key_material(scope)`. The `POST /jobs/run` response returns
  it **once** (wrapped when `wrap_key` is given — DPS cannot unwrap a wrapped key, so a caller who wants
  DPS to reuse a key passes it in clear over TLS). The clear key is sealed into `key_enc` for the job's
  lifetime only and purged at terminal state (transient custody; DPS never returns it from a GET and never
  keeps it after the job). This is the D2 reading for durable jobs; the same rule covers scans.
- **synthesize**: one `SynthesisSeed` per job, same custody rules.
- **job group**: `POST /api/v1/job-groups` generates a `KeyMaterial` + `SynthesisSeed`, returns both once,
  and stores only `kid` + `seed_fingerprint` (`sha256(seed)[:16]`). Every job with `group_id` must carry
  matching material (`group_key_mismatch` otherwise). DPS never stores a group key.

### 6.2 Anchors

M2 changes `dps/engine/transform/apply.py` (with tests): `ApplyOptions` gains `anchor: str | None = None`;
`apply_plan` uses it when set, else M0's `anchor_for` (public since M0 Task 22; it was `_anchor_for` in the
first M0 draft). L2 computes the anchor per row:

- if the snapshot marks an `anchor` column: `f"{entity_type}:{hash_value(to_engine_text(value))}"` — the
  exact string M0's `anchor_for` builds for the same entity, so L1 and L2 agree on date shifts and
  personas for the same customer across systems;
- else: `f"row:{hash_value(canonical key text)}"` where canonical key text is
  `"|".join(to_engine_text(v) for v in key)`.

Reveal of an L2 output works through L1 `/reveal`: the evidence pack's `reveal_map` gives per-path
`{entity_type, method, params, anchor_path}`; the caller (or `tools/reveal_rows.py`) reveals the anchor
column first, recomputes the anchor, then builds `RevealHint`s per row. `date_shift` on a table whose anchor
column is not reversibly transformed is allowed but marked `reveal: false` in the reveal map.

### 6.4 `BatchTransformer`


Per row: convert values with `to_engine_text`; build a `Plan` = the whole-value entries from `ColumnPlan`s
(a synthetic `Finding(locator=Locator(path=…), detectors=["snapshot"], …)` per non-null value, `[*]`
paths expanded against the document) + span findings from running the `Detector` over `text_column`
values (and, for Mongo with `unclassified="detect"`, over unclassified leaves) planned with
`build_plan(…, fpe_enabled=engine.fpe_enabled)`; call `apply_plan(plan=…, options=ApplyOptions(…,
anchor=row_anchor), data=row_doc)`; convert back with `from_engine_text`; collect originals with
`collect_originals` and run `verify_output` **per row** against that row's own outputs (kept values
excluded): exact fixed points for originals of ≥ 4 characters, cross-field containment for ≥ 8 (a
whole-batch sweep flags a short original inside another row's realistic surrogate or FPE output and would
fail healthy jobs at L2 volumes). Under `strict`, any hit raises `LeakageError` and the **batch** is not
written (the unit that fails closed stays the batch). After the write, a post-write detector sample re-reads
written rows (`verification.post_sample`). Engine counters (`TRANSFORMS`, `FINDINGS`) are incremented per
batch, never per value label.

### 6.5 Cross-system consistency

Same key material + `field_scoped: false` + the same entity type and method for joinable columns + the
same canonical text (`to_engine_text`) ⇒ identical tokens across Oracle, Mongo and PG. For `fpe_digits`
this holds between a numeric column and a text column holding the same digits (`10000123` and
`"CUST-10000123"`), and with L1 documents, because every plan uses `leading_zero: preserve` (§0 amendment
2026-10-12, B1): a token never gains a leading zero that a NUMBER/bigint column would drop. The M3 check
`POST /api/v1/job-groups/{id}/consistency-check {"pairs": [{"job_id", "path"}, …], "sample": 1000}` reads
up to `sample` transformed key values from each job's *target* and returns overlap counts only.

## 8. Auth, scopes, audit across milestones

### 8.1 Scopes (M0's `SCOPES`, unchanged): `detect obfuscate synthesize reveal jobs scan admin`

`jobs` covers connections, discovery, snapshots, runs, groups, evidence; `scan` covers scans; `admin` covers
tenants, keys, audit, queue, posture, **and is additionally required** for `in_place`/`append` writes to a
`production`-tagged connection and for changing the `production` tag. Tenant resolution stays M0's
`resolve_tenant` (`X-DPS-Tenant`); every M2+ handler uses `request.state.tenant_id` with `acquire()`.
Tenant ids starting with `_` are reserved for DPS pseudo-tenants (`_system`); from M2 on `resolve_tenant`
refuses them (403 `tenant_reserved`), even for wildcard keys, and the admin tenant API (M5) validates ids with
`^[a-z0-9][a-z0-9_-]{0,62}$`.

### 8.2 Errors

M2+ routers raise `DpsHttpError(status, code, detail, extra=None)` (new in `dps/layers/api/errors.py`)
rendered as `{"detail": str, "code": str, **extra}`; M0's `{"detail"}` responses stay valid (code absent).
M1's `dps.errors.CodedError` / `dps.layers.api.common.CodedHTTPException` use the same wire shape; M2's
`install_error_handlers` renders both (one wire format, two raise sites). As integrated (2026-10-12):
one handler, `dps.auth.coded_http_exception_handler`, is registered by `create_app` for every
`HTTPException` and renders any that carries a `code` (M1's `CodedHTTPException`, `dps.auth`'s
`CodedAuthHTTPException`) as `{"detail", "code"}`; `DpsHttpError` adds `**extra`; the L1 path
(`run_engine`) and M2's `to_http` both keep a `CodedError`'s (or a coded `HTTPException`'s) own status
and code; a strict audit refusal is 503 `audit_unavailable` on both.

### 8.3 Keys and audit

M0 static keys remain. M2 adds `DbAuditSink` (batched background writer to `dps_audit_log`, a structured
log line written synchronously first, like `di/audit.py`) chosen when the DB is configured;
`DPS_AUDIT_STRICT=true` (required in prod) turns a saturated queue into 503. M5 adds `DbKeyStore`
(snapshot cache refreshed every `DPS_KEY_CACHE_SECONDS`, keeping M0's synchronous `KeyStore.lookup`) and
`ChainKeyStore(static, db)`; keys are `dps_` + 32 urlsafe chars, stored as `hash_key()` sha256.
Audit rows of requests refused before a tenant is known (401) carry tenant `-`; operator CLI rows (M5
`dps.keys_cli`) and retention rows carry `_system`. Neither pseudo-tenant can be selected through the API.

**LLM exposure (spec P1, §10).** M0's process counter `dps_llm_raw_pii_sent_total` stays. M5 adds the
tenant dimension: `dps_llm_raw_pii_sent_by_tenant_total{tenant_id}` and
`dps_llm_exposure_blocked_by_tenant_total{tenant_id}` (incremented by the gateway's egress verifier, §10),
`AuditEvent.counts.llm_calls` / `counts.llm_raw_values` per request (rolled up per tenant per day), and the
alert rules `DpsRawPiiSentToLlm` (any increase, critical) and `DpsLlmExposureBlocked` (warning) in the
OpenShift manifests. The tenant comes from the `dps.observability.CURRENT_TENANT` context variable that
`run_engine` (L1) and the worker handlers (L2/L3) bind.

## 9. API route map (all milestones)

Base `/api/v1`; JSON unless stated; list endpoints take `limit` (1–200, default 50) + opaque `cursor` and
return `{"items": [...], "next_cursor": str | null}`; mutating job endpoints honour `Idempotency-Key`
(durable, per tenant, through `dps_job_idem`). From M1 the L1 engine routes (`/detect`, `/obfuscate`,
`/synthesize`, `/reveal`, `/documents/*`, `/schema/synthesize`) honour it too (replica-local replay cache,
M1 plan Task 19B); the header must match `^[A-Za-z0-9_.:-]{1,128}$` (422 `idempotency_key_invalid`), the
same key with a different body is 422 `idempotency_key_reused`, a replay carries `Idempotent-Replay: true`
(the header M2's job routes already send).
**One `Idempotency-Key` contract for Layer 1 and the job routes (integration of M1 and M2,
2026-10-12).** Both use the same header names (`Idempotency-Key`, `Idempotent-Replay`, the latter
exposed through CORS), the same key regex and the same codes and details (`dps.errors`
`IDEMPOTENCY_KEY_*`, `dps.layers.api.idempotency`): 422 `idempotency_key_invalid` for a malformed key
and 422 `idempotency_key_reused` for the same key with another request. On the job routes a durable
key is bound to a keyed fingerprint of its request — `dps.secrets.keyed_fingerprint` under an HKDF
subkey of the job KEK (info `dps.idempotency_fp`, salt the route template) over the raw body, stored
in `dps_job.idempotency_fp` (migration 010) — so a key reused with another body, or on another job
route, is refused before any validation instead of replaying a different job. Jobs admitted without a
KEK (or before 010) have no fingerprint and keep the key-only replay. The console mints a new key
whenever the run request it submits changes.

**L1 replay custody (amendment 2026-10-12, decision D2 stateless key custody).** The L1 replay cache
stores, per scope hash (`sha256(tenant, key id, route template, Idempotency-Key)`), only the request body
hash, the original trace id and a timestamp — never key material, a DEK, a synthesis seed, an output or a
value, and routes never pre-generate material for it. Same key + same body within the TTL **re-runs the
engine** and answers with `Idempotent-Replay: true`, the original `trace_id` and audit outcome `replayed`.
Results are byte-identical only when the caller supplied its own `consistency.key_material` /
`synthesis_seed`; otherwise the replay returns fresh key material, which is safe because a Layer 1 call has
no side effects (documented in `docs/technical/api-m1.md`). Entries are recorded after a 2xx response only.
Same key + different body → 422 `idempotency_key_reused`. Durable job idempotency (`dps_job_idem`) is
unaffected: a job row is the durable record, and the job's key material is still returned once and never
kept (§6.1).
The same L1 routes stream large arrays as NDJSON (M1 plan Task 19A): request `Content-Type:
application/x-ndjson` (first line = the envelope without `data`, then one item per line) and/or response
`Accept: application/x-ndjson` (a `header` line, one `item` line per array element, a closing `report`
line; an `error` line ends a stream that failed closed).

## 13. Artefact storage (`dps/storage.py`)

```python
class StoredObject(BaseModel): store: Literal["local", "s3"]; key: str; bytes: int; sha256: str; content_type: str
class ObjectStore(Protocol):
    name: Literal["local", "s3"]
    async def put(self, key: str, data: bytes | AsyncIterator[bytes], *, content_type: str) -> StoredObject
    async def get(self, key: str) -> bytes
    def stream(self, key: str, *, chunk: int = 1 << 20) -> AsyncIterator[bytes]
    async def delete(self, key: str) -> None
    async def exists(self, key: str) -> bool
class LocalObjectStore:  def __init__(self, root: Path) -> None     # refuses keys escaping root
class S3ObjectStore:     def __init__(self, *, bucket: str, endpoint_url: str | None, region: str,
                                       access_key_id: str, secret_access_key: str, force_path_style: bool) -> None
                         # boto3 in asyncio.to_thread; multipart for > 16 MiB
def artefact_store(settings: Settings) -> ObjectStore
def target_store(conn: Connection, settings: Settings) -> ObjectStore   # files targets (s3/pvc connections)
class ArtefactService:
    def __init__(self, store: ObjectStore, *, acquire: AcquireFn) -> None   # acquire = db.acquire (API) | db.acquire_queue (workers)
    async def save(self, *, tenant_id: str, job_id: str, kind: str, data: bytes, content_type: str,
                   meta: dict[str, Any] | None = None) -> str          # returns artefact id, inserts dps_artefact
    async def open(self, tenant_id: str, artefact_id: str) -> tuple[Artefact, AsyncIterator[bytes]]
    async def delete_for_job(self, tenant_id: str, job_id: str) -> int
```

Object key layout: `t/<tenant_id>/<job_id>/<artefact_id>.<ext>` (artefacts) and
`<prefix>/<job_id>/part-<partition_no:05d>-<file_no:03d>.<ext>` + `<prefix>/<job_id>/manifest.json`
(`files` targets). Keys never contain values, URLs or labels. Screenshots are PNG; masked captures cover
detected rendered values with filled boxes before encoding; unmasked originals of pages with rendered PII
are never stored unless `scan_store_unmasked_originals=true` (local only).
